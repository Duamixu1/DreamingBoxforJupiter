# MVP · 照片生成回忆旅程

> 上传几张旅行照片，Tripo 把每个地方做成盒子里的一个微缩站点；火车或飞机把它们连成一条旅程；手摇，重游一遍。

当前原型的旅程是写死的五站。这一版把「内容」交给用户：**每一张照片 = 一站**，盒子里的旅程就是你们真实走过的路线。

---

## 一、一句话体验

送礼的人在手机上传 3–5 张旅行照片，每张写一句话，再写一封信；几分钟后，收礼人打开木盒，摇动摇柄，小火车（或小飞机）依次经过这些地方。每到一站，当年那张照片像明信片一样立在路边；旅程的终点是那封信。

---

## 二、关键判断：Tripo 做「地标」，不做「整个场景」

这是整个方案能不能成立的前提，先说清楚。

| | 能做好 | 做不好 |
| --- | --- | --- |
| **Tripo**（图 / 文 → 3D 模型） | 单个主体：灯塔、教堂、咖啡馆、雪山、帆船、摩天轮 | 一整张风景照（海滩 + 人群 + 天空），人像 |
| **World Labs Marble**（图 → 3D 世界） | 一整片可漫游的空间，Gaussian Splat | 在 Jupiter 上实时画：每帧 9 个视点 × 50 万粒子，RK3566 带不动；也没法和火车滚动的世界拼接 |

所以每张照片拆成三部分处理：

1. **地标** → 识别照片里最有辨识度的主体（「那座白色灯塔」）→ Tripo 生成 3D 微缩模型，放在站点中央。
2. **氛围** → 同一次识别给出地貌（海边 / 山野 / 城市 / 森林 / 雪地 / 田园）、时段（清晨 / 白天 / 黄昏 / 夜晚）、主色 → 驱动我们已有的程序化布景模板：地面、天色、树、水、灯光。
3. **照片本身** → 到站时作为一张明信片立在轨道边。这一刻让人一眼看懂「这是我的照片变出来的」。

> 这样 Tripo 是核心链路，不是装饰：没有它，每一站就只是通用布景；有它，每一站才是「那个地方」。

World Labs 留作后续：可以把它生成的世界预渲染成每站的远景背板，但不进 MVP。

## 三、用户流程

### 制作端（送礼人，手机网页）

```
S1 送给谁        称呼 · 选交通工具（火车 / 飞机）
S2 传照片 ★      3–5 张，拖动排序 = 旅程顺序；每张可写一句话（选填）
S3 确认 ★★       AI 识别结果逐站展示：「我们从这张照片里看到了：灯塔 · 海边 · 黄昏」
                 每站可以改地标（换成照片里的另一个东西）、改地名
S4 写信          终点那封信
S5 生成          约 2–3 分钟，逐站出现预览 → 得到一个链接 / 二维码
```

S3 是命门：AI 认错了（把「那家面馆」认成「建筑」），用户在这里一键改掉，而不是收到一个错的礼物。可以直接沿用 [方案1-Web端操作流程](../../方案1-Web端操作流程.md) 和 [方案3-AI信息提取](../../方案3-AI信息提取.md) 里「AI 提出来，你点头或改掉」的交互。

### 体验端（收礼人，Jupiter 木盒）

和现在一样，只多了两件事：

- 开门 → 摇动 → 火车 / 飞机出发；**站点数量、地标、天色都来自照片**
- **到站明信片**：经过每站中心时，那张照片以立牌的形式出现在轨道边，停留到下一站
- 终点 → 继续摇 → 信件展开

交互仍然只有「开门」和「摇」两件事，不加触摸、不加按钮（原方案第 02 页的约束不变）。

## 四、交通工具：火车和飞机

| | 火车（P0） | 飞机（P1） |
| --- | --- | --- |
| 适合 | 同一座城市、一次自驾、国内旅行 | 跨国、跨海、多个城市 |
| 画面 | 现有：轨道、站台、烟 | 飞机悬在中景高度，脚下是云层；到站时云层散开，露出下面的地标 |
| 改动量 | 已完成 | 换载具模型 + 去掉轨道 + 加一层随世界时间流动的云海，约 1 天 |

两种都是「世界从它身边经过」，所以世界时间、手摇、音乐的逻辑完全复用。MVP 一份礼物只选一种；混合（坐火车到机场、再换飞机）放到后续。

## 五、技术链路

```
手机上传照片
   │
   ▼
① 识别（视觉大模型，每张一次）
   输出：{ 地名, 地貌, 时段, 主色[3], 地标: { 名称, 在图中的位置 }, 一句话描述 }
   │
   ├──► ② 地标裁切 → Tripo image_to_model（face_limit ≈ 3000，贴图内嵌）
   │        地标不清楚时 → Tripo text_to_model（「miniature diorama of …」）兜底
   │        单个模型约 1–2 分钟，5 站并行
   ▼
③ 生成 journey.json（每站：地貌模板、天色、地标 GLB、照片、文案）+ 打包素材
   │
   ▼
④ Jupiter 木盒：?journey=<id> 拉取 → 按站点生成世界 → 手摇
```

**journey.json（草案）**

```json
{
  "recipient": "亲爱的你",
  "vehicle": "train",
  "stations": [
    {
      "name": "青岛 · 小麦岛",
      "biome": "seaside",
      "timeOfDay": "dusk",
      "palette": ["#f2b27a", "#3e8db3", "#e6d3a3"],
      "landmark": { "glb": "landmarks/1.glb", "label": "白色灯塔" },
      "photo": "photos/1.jpg",
      "caption": "那天风很大，你说灯塔像一根粉笔"
    }
  ],
  "letter": { "greeting": "亲爱的你：", "lines": ["…"], "signature": "— 某某" }
}
```

现有原型已经具备的：世界时间、手摇、音乐、信件、模型槽位（GLB 自动缩放和落地）、截图。要改的主要是把 `config.js` 里写死的 `STORY` 换成读取 `journey.json`，以及把五个写死的站点拆成**六个可复用的地貌模板**。

## 六、MVP 范围

**做**

- 3–5 张照片 → 同样多的站点，顺序 = 旅程顺序
- 六个地貌模板：海边、山野、城市、森林、雪地、田园
- 每站 1 个 Tripo 地标，氛围由照片驱动的天色和主色决定
- 到站明信片
- 火车（P0）、飞机（P1），每份礼物选一种
- 手机网页制作端：上传、确认改错、写信、生成链接
- 生成失败的兜底：识别失败 → 用户选地貌；Tripo 失败或超时 → 该地貌的默认地标

**不做**

- 人物建模（隐私风险高，Tripo 做人像也不稳）；照片里有人只出现在明信片上
- World Labs 全景世界、Gaussian Splat
- 账号系统、礼物编辑、多段交通混合
- 地图选择、分支路线（原方案第 11 页的约束不变）
- 超过 5 站（每站约 13 秒常速，5 站 ≈ 75 秒，正好落在原方案 60–90 秒的目标里）

## 七、风险与对策

| 风险 | 对策 |
| --- | --- |
| 照片没有明确地标（美食、自拍、室内） | S3 让用户点选照片里的另一个东西；或直接用文字描述生成；再不行用该地貌默认地标 |
| Tripo 输出风格不统一（有的写实、有的卡通） | 统一换成 Lambert 平光材质（已实现）+ 微缩比例 + 按照片主色做轻度调色；生成提示词统一加 miniature diorama 风格词 |
| 生成要等几分钟 | S5 逐站出现预览；现场演示时提前生成一份完整旅程，只现场生成一站 |
| 面数超标拖慢 Jupiter | 调用时设 `face_limit`；加载时已有面数检查 |
| 照片隐私 | 照片只存在这份礼物的素材包里，链接不公开索引；不用于其他用途 |

## 八、演示方案（10/17 现场）

1. **预制一份完整旅程**：用团队真实的旅行照片，5 站，装进木盒，评委直接开门摇。
2. **现场生成一站**：评委用手机拍一张眼前的东西（或从相册选一张）→ 约 2 分钟 → 这一站出现在旅程的最后一站之前。这一步直接证明「照片 → Tripo → 盒子里的世界」是真的，不是预录的。
3. 讲述只用一句话：**「你们去过的地方，被装进了这个盒子；摇一摇，再走一遍。」**

## 十、验收标准

- 上传 5 张照片，10 分钟内（含等待）在手机上得到一份可打开的礼物
- 木盒里出现 5 站，每站的地标能被送礼人认出是「那个地方」
- 每站到站时，明信片显示的是对应的原照片
- 摇速控制世界速度、停手世界停下、音乐跟随摇没摇 —— 和现有原型一致
- 任何一站生成失败，旅程仍然完整可摇（用默认地标兜底）
